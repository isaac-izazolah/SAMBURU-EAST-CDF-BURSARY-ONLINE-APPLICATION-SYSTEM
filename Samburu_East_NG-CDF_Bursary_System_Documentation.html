1. System Overview

1.1 Purpose

The Samburu East NG-CDF Bursary Online Application System is a web-based platform designed to digitize and streamline the bursary application and allocation process for the Samburu East Constituency National Government Constituency Development Fund (NG-CDF). The system replaces manual paper-based processes with an efficient online workflow that serves both applicants and administrators.

1.2 Objectives

  • Enable students to apply for bursaries online from anywhere
  • Reduce paperwork and manual processing time
  • Provide transparent tracking of application status
  • Automate bursary allocation based on configurable rules
  • Generate comprehensive reports for decision-making
  • Maintain a secure audit trail of all actions

1.3 Target Users

  • Applicants: Students seeking bursary funding from Samburu East NG-CDF
  • Administrators: Staff managing applications, allocations, budgets, and reports
  • Super Administrators: Senior staff with full system access including audit logs

3.1 Directory Structure

3.2 Request Flow

  1. User visits a page (e.g., apply.php)
  2. PHP includes shared headers (includes/header.php) for consistent layout
  3. Page-specific PHP logic processes form submissions or queries the database
  4. Data is rendered in HTML with Bootstrap styling
  5. JavaScript (main.js, admin.js) handles dynamic interactions
  6. Shared footers (includes/footer.php) load JS libraries and close HTML

3.3 Admin Request Flow

  1. Admin visits admin page (e.g., admin/applications.php)
  2. admin/header.php checks authentication via requireAdminLogin()
  3. Role-based permissions gate access to specific features
  4. Page renders with sidebar navigation and topbar
  5. DataTables provide server-side or client-side data tables with filtering
  6. admin/footer.php loads all JS libraries including Summernote editor

4. Database Design

4.1 Database Name

samburu_bursary

4.2 Entity Relationship Summary

The system uses 14 tables with the following relationships:

  • wards 1:N applications (one ward has many applications)
  • applications 1:N allocations (one application can have multiple allocations)
  • applications 1:N application_tracking (status history)
  • applications 1:N uploaded_documents (attached files)
  • administrators 1:N applications (created_by)
  • administrators 1:N allocations (allocated_by)
  • administrators 1:N announcements (created_by)
  • administrators 1:N audit_logs (admin_id)
  • administrators 1:N login_logs (admin_id)
  • budgets 1:N allocations (budget_id)
  • allocation_rules used by allocations engine

6.2 Application Form (apply.php)

Multi-section form with 4 progressive steps:

  1. Personal Information: Full name, email, phone (optional), gender, date of birth, national ID/birth cert, ward selection, location
  2. Academic Information: Institution name, type (Secondary/TVET/College/University), level (Certificate/Diploma/Degree), year of study, course name
  3. Financial Information: Total fees, fees paid, auto-calculated outstanding balance, amount requested, payment option (Bank/M-Pesa), account details
  4. Document Upload: National ID, admission letter, fee statement, previous results, special needs doc, additional doc (PDF/JPG/PNG, max 5MB each)

Output: Generates unique application number (format: SECDF2025XXXXXX) and displays acknowledgement slip.

6.3 Application Status Check (check_status.php)

Allows applicants to check status using application number and date of birth. Features:

  • Status display with color-coded badges
  • Auto-refresh via AJAX every 30 seconds
  • Print/download PDF of status details

9. Budget and Allocation System

9.1 Budget Management

  • Budgets are created per financial year (e.g., 2025/2026)
  • Only one budget can be active at a time
  • The active budget determines available funds for allocation
  • Allocated and remaining amounts are tracked in real-time

9.2 Allocation Engine (includes/allocation_engine.php)

The allocation engine automates bursary distribution:

  1. Validation: Checks that an active budget exists with remaining balance
  2. Query: Fetches all approved applications not yet allocated
  3. Rule Matching: For each application, finds the highest-priority matching rule based on:
    • Institution type (Secondary/TVET/College/University)
    • Level (Certificate/Diploma/Degree)
    • Special category (None/Orphan/Disability)
  4. Amount Calculation:
    • If rule has fixed_amount: uses that amount
    • Otherwise: generates random amount between min_amount and max_amount
  5. Budget Cap: Allocation is capped at remaining budget
  6. Transaction: All allocations wrapped in a database transaction for data integrity

9.3 Default Allocation Rules

24 rules are seeded covering all combinations of:

  • 4 institution types: Secondary, TVET, College, University
  • 3 levels per type (where applicable)
  • 3 categories: None, Orphan, Disability

Orphan and Disability categories receive priority (higher priority number) and potentially higher allocation amounts.

12. Security Features

12.1 Authentication

  • Password hashing using PASSWORD_DEFAULT (bcrypt)
  • Session-based authentication for admin users
  • CAPTCHA verification on admin login (GD-generated image)
  • Password reset via secure token with expiry
  • Session timeout and secure session handling

12.2 Authorization

  • Role-based access control (RBAC) on all admin pages
  • Permission checks before feature access
  • Super admin-only areas (user management, audit logs)

12.3 Data Protection

  • CSRF Protection: All forms include CSRF tokens, verified on submission
  • Input Sanitization: sanitize() function applies htmlspecialchars() + stripslashes() + trim()
  • SQL Injection Prevention: PDO prepared statements used throughout
  • XSS Prevention: All user output escaped with htmlspecialchars()
  • File Upload Security: Extension whitelist, MIME type validation, size limits

12.4 Server Security

  • .htaccess blocks access to sensitive files (.sql, .md, .log, .env)
  • Security headers: X-Content-Type-Options, X-Frame-Options, X-XSS-Protection
  • Error logging enabled, display_errors disabled in production

12.5 Audit Trail

  • All admin actions logged with: admin ID, action, description, IP address, user agent, timestamp
  • Login attempts tracked (success/failure)
  • Audit logs viewable by super admin only

15. Deployment and Installation

15.1 Requirements

  • PHP 7.4 or higher
  • MySQL 5.7 or higher
  • Apache web server (XAMPP recommended for development)
  • GD Library PHP extension (for CAPTCHA)

15.2 Installation Steps

  1. Place project files in web server document root (e.g., C:/xampp3/htdocs/PROJECTS/SAMBURU EAST CDF/)
  2. Create MySQL database named samburu_bursary
  3. Import database/samburu_bursary.sql to create tables and seed data
  4. Configure database credentials in config/database.php
  5. Ensure /uploads/ directory is writable
  6. Access the public site at the configured URL
  7. Access admin panel at {URL}/admin/

15.3 Default Admin Credentials

EmailPasswordRole
admin@samburueastcdf.go.keadmin123super_admin
Note: Default passwords should be changed immediately after first login for security.

15.4 Important Notes

  • Ensure PHP has write permissions to the uploads directory
  • Configure PHP upload_max_filesize and post_max_size to at least 5MB
  • Set PHP timezone to Africa/Nairobi in php.ini if not set in code
  • For production, ensure HTTPS is configured
  • Regular database backups are recommended
